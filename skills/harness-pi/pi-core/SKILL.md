# pi core: the normal harness

"Pi" is the terminal coding agent. Its core is three layers plus supporting libraries. This
skill describes how they fit and how a run flows through them. It was read from source at
the commit above; no code was run. Source paths are relative to the pi repository root.
When a clone disagrees, the clone wins.

```
pi-coding-agent   CLI, sessions, tools, extensions, modes     (packages/coding-agent)
      |
pi-agent-core     in-memory loop: Agent, events, hooks        (packages/agent)
      |
pi-ai             providers, models, messages, streaming      (packages/ai)

side libraries: pi-tui (UI), pi-mcp (MCP client), pi-codemode (script sandbox), pi-telemetry
```

Design stance (README): a minimal, extensible harness you make your own. Sub-agents and
plan mode are deliberately not built in; the expectation is that users add them with an
extension, a skill, or an installed package.

## 1. pi-ai: the provider layer

Entry points are methods on a `Models` registry (`packages/ai/src/models.ts`), not free
functions: `createModels()` builds one, `builtinModels()` (`providers/all.ts`) registers
the built-in providers. Legacy global `stream`/`complete`/`streamSimple`/`completeSimple`
remain in `compat.ts`.

- **Calls.** `models.stream`, `complete`, `streamSimple`, `completeSimple` (the "simple"
  forms take `reasoning` and thinking budgets), plus `streamDeferred`/`fetchDeferred`/
  `cancelDeferred` for deferred responses, `generateImages`, `classify`. Reads:
  `getModels`, `getModel`, `getAvailable`, `getAuth`; `login`, `logout`, `refresh`.
- **Provider** interface: `id`, `auth`, `getModels()` (sync, last-known), optional
  `refreshModels()`, `stream`/`streamSimple(model, context, options)`. About 42 built-in
  provider factories (anthropic, openai, google, bedrock, vertex, azure, openrouter,
  mistral, groq, xai, github-copilot, and many more). A faux provider exists for tests.
- **Messages** (`types.ts`): `SystemMessage` (carries prompt sections and tool additions or
  removals as deltas), `UserMessage`, `AssistantMessage` (content blocks, `usage`,
  `stopReason`), `ToolResultMessage`. Content blocks: text, thinking (with signature,
  possibly redacted), image (base64), tool call (`arguments` JSON, `argumentsError?`).
  Stop reasons: `pending | stop | length | toolUse | error | aborted | deferred`.
- **Context** is `{ systemPrompt?, messages, tools? }`, folded into a normalized
  transcript before reaching a provider.
- **Streaming protocol**: `AssistantMessageEvent` = `start`, `text_*`/`thinking_*`/
  `toolcall_*` with `start`/`delta`/`end`, then `done` (`stop | length | toolUse |
  deferred`) or `error` (`aborted | error`), consumed through `EventStream`.
- **Tools** are `{ name, description, parameters }` with typebox `TSchema`;
  `validateToolArguments` coerces and validates arguments.
- **Thinking levels**: `minimal | low | medium | high | xhigh | max` (plus `off`), mapped
  per model by `thinkingLevelMap`; `clampThinkingLevel` picks the nearest supported one.
- **Usage and cost**: `usage` has input, output, cacheRead, cacheWrite, reasoning and a
  `cost` breakdown; `calculateCost` handles tiered rates.
- **Auth**: a provider declares `apiKey` and/or `oauth` auth. A `CredentialStore`
  serializes credential updates; OAuth providers include anthropic, openai, openai-codex,
  github-copilot and openrouter. Env-var keys come from `env-api-keys.ts`.
- **Overflow and retry helpers**: `isContextOverflow` (regex list plus a silent-overflow
  check against the context window), `isRecoverableLength`, `retryAssistantCall` and
  `retryDelayMs` (exponential), `retryProviderRequest`. **Nothing inside `ai` or
  `agent` calls them**; the host does.
- **Model catalog**: `models.generated.ts` is generated by `npm run generate-models`
  (network: models.dev, OpenRouter, provider APIs); `hydrate-model-data` rebuilds offline;
  `Models.refresh` and a `ModelsStore` (etag-based) update at runtime.

## 2. pi-agent-core: the loop

Files: `agent.ts` (`Agent` class), `agent-loop.ts` (the loop), `types.ts`, `proxy.ts`,
`stream-fn.ts`. Purely in-memory; no persistence, no retry, no overflow handling.

### The Agent

`new Agent(options)` takes `initialState`, `streamFn` (a `Models.streamSimple` fits),
`convertToLlm`, `transformContext`, `getApiKey`, and the hooks in §2.3, plus
`steeringMode`/`followUpMode` (default one-at-a-time), `toolExecution` (default
`parallel`), `transport`, `sessionId`, `thinkingBudgets`.

Methods: `prompt(message | string, images?)` (throws if a run is active), `continue()`,
`steer(msg)`, `followUp(msg)`, queue clear/peek helpers, `abort()`, `waitForIdle()`,
`reset()`, `subscribe(listener(event, signal))`. State: `systemPrompt`, `model`,
`thinkingLevel`, `tools`, `messages`, `isStreaming`, `streamingMessage`,
`pendingToolCalls`, `errorMessage`.

### The loop, step by step (`runLoop`, `agent-loop.ts`)

1. Declare tool changes; emit `agent_start`, `turn_start`, and `message_start/end` for each
   prompt message. Poll steering messages once.
2. **Outer loop** over follow-ups; **inner loop** while tool calls are pending or queued
   messages exist.
3. For each turn after the first: `prepareNextTurn` (may replace context, model or thinking
   level, or append messages), re-poll steering, emit `turn_start`, emit queued messages,
   then `prepareRequest` (runs before every provider request).
4. `streamAssistantResponse`: `transformContext` (AgentMessage level), then
   `convertToLlm` (to LLM messages), then normalize, then `getApiKey`, then
   `streamFn(model, context, options)`. Stream events become `message_start/update/end`.
5. If `stopReason` is `error` or `aborted`: `finishTurn`, `turn_end`, `agent_end`, stop.
6. If `stopReason` is `length`, every tool call in the message gets an error result.
   Otherwise execute the tool calls (§2.2).
7. `finishTurn` (may return `{action: "end"}` to stop without polling queues), `turn_end
   {message, toolResults}`, poll steering for the next inner iteration.
8. With nothing left inside: poll follow-ups. If none, emit `agent_end`.

Steering messages enter after the current assistant turn's tools; follow-ups enter only
when the agent would otherwise stop.

### Tool execution

Sequential if `toolExecution` is `"sequential"` or any called tool has
`executionMode: "sequential"`; otherwise parallel. Parallel mode prepares every call in
order, runs executions concurrently, emits `tool_execution_end` in completion order, and
emits the `toolResult` messages in source order. Preparation: unknown tool becomes an error
result, then `prepareArguments`, then `validateToolArguments`, then `beforeToolCall`
(which can block). `afterToolCall` replaces result fields one by one (no deep merge). A
tool batch ends the loop only if every result has `terminate: true`.

`AgentTool` extends the ai `Tool` with `label`, `prepareArguments?`, `outputSchema?`,
`execute(toolCallId, params, signal?, onUpdate?) => AgentToolResult`, `executionMode?` and
`replay?: "never" | "safe"`. A result is `{content, details, structuredContent?, usage?,
isError?, terminate?}`; throw or set `isError` to fail.

### Events and hooks

`AgentEvent`: `agent_start`, `agent_end {messages}`, `turn_start`, `turn_end {message,
toolResults}`, `message_start`, `message_update` (assistant streaming only), `message_end`,
`tool_execution_start` (before validation), `tool_execution_update`, `tool_execution_end`
(after `afterToolCall`, with `durationMs`). The Agent awaits listeners before going idle.

`AgentLoopConfig` hooks: `convertToLlm` (required, must not throw), `transformContext`,
`getApiKey`, `prepareRequest`, `prepareNextTurn`, `finishTurn`, `getSteeringMessages`,
`getFollowUpMessages`, `toolExecution`, `beforeToolCall` (`{block?, reason?, terminate?}`),
`afterToolCall` (`{content?, details?, structuredContent?, isError?, usage?, terminate?}`).

### Custom message types

`AgentMessage = Message | CustomAgentMessages[...]`. `CustomAgentMessages` is empty and
extended by declaration merging on `"@earendil-works/pi-agent-core"`. Your `convertToLlm`
must map or filter every custom role.

Known rough edges: `Agent`'s `prepareNextTurn` option takes a signal while the loop config
type takes a context (bridged by `prepareNextTurnWithContext`); a JSDoc example still names
an old package scope.

## 3. pi-coding-agent

### Layout

`src/cli.ts` and `src/main.ts` (entry), `src/index.ts` (SDK exports), `src/rpc-entry.ts`
(second binary forcing `--mode rpc`). `src/core/`: `agent-session.ts`, `sdk.ts`,
`session-manager.ts`, `settings-manager.ts`, `system-prompt.ts`, `resource-loader.ts`,
`skills.ts`, `compaction/`, `extensions/` (loader, runner, types), `tools/`,
`auth-storage.ts`, `model-registry.ts`, `package-manager.ts`. `src/modes/`: `interactive/`,
`print-mode.ts`, `rpc/`, `json-event.ts`. `src/extensions/`: built-in extensions (codemode,
mcp, llama, tool-search). Docs: `packages/coding-agent/docs/` (start with `how-pi-works.md`,
`extensions.md`, `sdk.md`, `rpc.md`, `session-format.md`, `settings.md`).

### Run modes

Chosen in `main.ts`: `--mode rpc`, `--mode json`, print mode (print flag or non-TTY), else
interactive. Embedding options: in-process through the SDK (`createAgentSession(options)`
in `core/sdk.ts`, `createAgentSessionRuntime` adds new/switch/fork/import), a subprocess
speaking RPC (`pi --mode rpc`, with the TypeScript `RpcClient`), or one-shot `--print` /
`--mode json`. Examples: `packages/coding-agent/examples/sdk/` (01-minimal to
14-codemode-mcp) and `examples/extensions/` (about 80 files).

### AgentSession

`AgentSession` (`core/agent-session.ts`) wraps one `Agent`, a `SessionManager` and a
`SettingsManager`. Its constructor subscribes `_handleAgentEvent`, which persists messages,
fires extension events, and drives auto-compaction and auto-retry. Surface: `prompt`,
`steer`, `followUp`, `abort`, `setModel`/`cycleModel`, `setThinkingLevel`, `compact`,
`navigateTree`, `executeBash` (the `!` and `!!` commands; `!!` is excluded from context),
and scoped model sets.

- **Auto-compaction** is blocking and inline: before the next assistant response the
  session checks the threshold and awaits the summary (reasons `overflow` or `threshold`).
  Defaults: `reserveTokens` 16384, `keepRecentTokens` 20000. Manual `compact()` aborts
  the current operation first.
- **Auto-retry**: retryable provider errors retry with exponential backoff (defaults
  `maxRetries` 3, `baseDelayMs` 2000).

### Sessions

`SessionManager` writes JSONL, version 3, one file per session under
`~/.pi/agent/sessions/--<path>--/<timestamp>_<id>.jsonl`. First line is a `session`
header (version, id, cwd, optional parentSession). Every other line has `id`, `parentId`
(null for the root), `timestamp`, `type`. Entry types: `message`, `thinking_level_change`,
`model_change`, `usage`, `compaction` (with `firstKeptEntryId`), `branch_summary`, `custom`
(never in LLM context), `custom_message` (in LLM context), `label`, `session_info`,
`context_edit`. A `leafId` marks the active branch; abandoned branches stay in the file.
Fork and clone copy history into a new file. File creation is lazy (nothing is written
until a user or assistant message exists); each entry is then appended with
`appendFileSync`, with no fsync and no lock file.

Crash behavior: streamed text exists only in memory until the message completes. A crash
after an assistant tool call is saved and before its result leaves a dangling call; I
found no code that re-runs interrupted tool calls or model requests on resume. Crashes are
recorded in a crash log and the next start suggests `-r`. This is the main thing
`pi-durable` changes.

### Tools and the system prompt

Built-in tools: `read`, `bash`, `powershell`, `edit`, `write`, `grep`, `find`, `ls`.
Default-on: `read`, `bash`, `edit`, `write`; change with the `defaultTools` setting
(`+name`, `-name`). Each tool has an operations interface (`ReadOperations`,
`BashOperations.exec`, `EditOperations`, ...) so a backend can be swapped in-process. That
is an injection seam, not an isolation boundary: pi has no built-in permission system, and
extensions run with full process permissions. Sandbox the process (container, VM) if you
need a boundary.

### System prompt construction

The prompt is built from named sections and stored in the session as patches, not as one
string.

**Building.** `buildSystemPromptSections` (`core/system-prompt.ts`) returns an ordered map:
`preamble`, `tools`, `rules`, `docs`, `addendum`, `project_context`, `skills`, `cwd`, then
extension-defined sections (the built-in MCP extension adds `mcp_servers`). Every section
except the preamble is wrapped as `<name>...</name>`.

- `preamble`: fixed text ("You are an expert coding assistant operating inside pi...").
- `tools`: one line per selected tool that has a `promptSnippet`, plus a fixed note that
  custom tools may exist. Hidden tools are left out.
- `rules`: each selected tool's `promptGuidelines`, de-duplicated, plus fixed rules (be
  concise, show file paths) and a bash-only file-operations rule when `grep`, `find` and
  `ls` are not active.
- `docs`: pointers to pi's README, docs and examples for pi-related questions.
- `addendum`: `APPEND_SYSTEM.md` and every `--append-system-prompt`, joined by blank lines.
- `project_context`: `<project_instructions path=...>` blocks. The loader takes the first of
  `AGENTS.override.md`, `AGENTS.md`, `CLAUDE.md` found in the agent dir, then the cwd and its
  ancestors (`core/resource-loader.ts`).
- `skills`: name and description of each skill (`formatSkillsForPrompt`); bodies load on
  demand.
- `cwd`: the working directory. No date is inserted.

**Replacing it.** `SYSTEM.md` or `--system-prompt` (a literal string, or a path whose file
is read) replaces the default base. When a custom prompt is set, the `tools`, `rules` and
`docs` sections are dropped too, not only the preamble; appended text, project context,
skills and cwd stay. Discovery: an explicit option first, then `.pi/SYSTEM.md` (only if the
project is trusted), then `<agent-dir>/SYSTEM.md`. Project replaces global; there is no
merge. `APPEND_SYSTEM.md` is discovered the same way.

**Extension control.** The `before_agent_start` event receives a mutable
`systemPromptOptions` and a rendered `systemPrompt`. Editing sections is the preferred route
(for example setting `sections.mcp_servers`). Returning `{systemPrompt}` forces a whole
replacement for that run, which is projected onto each request and not stored.
`context_with_system` is request-local: it sees the full transcript and must keep the system
message at index 0, and its output is not persisted. A custom section with an invalid name
throws.

**Delivery and storage.** The `Agent` is created with an empty `systemPrompt`; the prompt
reaches the provider as `SystemMessage` entries in the transcript (the `pi-ai` format with
`content`, named `sections` where `null` deletes one, and `toolsAdded`/`toolsRemoved`). On
each run `_preparePromptAndToolLoadout` diffs the freshly built sections against the last
system message in the transcript (`diffSystemPromptSections`) and appends only what changed.
Compaction snapshots the sections into the transcript. The rendered string is never stored,
so on resume the options are rebuilt from the current files and any difference becomes a
new patch.

**Rebuild triggers.** The tool loadout changing and `extendResources` rebuild it. Context
files and skills are read only in `resourceLoader.reload()`, so edits to `AGENTS.md` or a
skill take effect after `/reload`.

**Caching.** Unchanged sections add no new message, so the cached prefix survives.
Providers that cannot represent section or tool deltas receive the full text, which can
break the prefix. A forced `systemPrompt`, a changed `cwd`, or changed `project_context`
alters the prefix. A cache warmer (`cache-warmer.ts`) refreshes session requests at about
90% of the model's cache TTL, tuned by `cacheRetention` or `PI_CACHE_RETENTION`.

Compare `pi-durable`, which stores the same patch format but ships no prompt text.

### Configuration

Global `~/.pi/agent/` (override with `PI_CODING_AGENT_DIR` or the SDK `agentDir`):
`settings.json`, `auth.json`, `models.json` (custom providers and endpoints),
`sessions/`, `extensions/`, `skills/`, `prompts/`, `themes/`. Project: `.pi/settings.json`
and the same folder names under `.pi/`; project settings load only after the project is
trusted. Key settings: `defaultProvider`, `defaultModel`, `defaultThinkingLevel`,
`defaultTools`, `compaction.*`, `retry.*`, `sessionDir`, `packages`, `extensions`,
`skills`, `prompts`, `themes`, `steeringMode`, `followUpMode`.

### RPC

`pi --mode rpc` reads JSONL commands from stdin (optional string `id`) and writes
`response` records, session events and `extension_ui_request` records to stdout. Commands
include `prompt` (with `streamingBehavior` steer or followUp), `steer`, `follow_up`,
`abort`, `new_session`, `get_state`, `get_messages`, `set_model`, `set_thinking_level`,
`compact`, `bash`, `switch_session`, `fork`, `clone`, `get_tree`, `get_commands`.
Single client over pipes; there is no attach to a running session. Details in
`docs/rpc-commands.md` and `src/modes/rpc/rpc-types.ts`.

## 4. Extending pi

**Extensions** are TypeScript modules loaded at runtime with jiti (`core/extensions/
loader.ts`; bundled binaries use a static loader). Discovery order covers `.pi/extensions/`,
`<agent-dir>/extensions/`, configured `extensions` paths and `pi -e <path>`; a directory
resolves through `package.json` `pi.extensions` then `index.ts`. The default export is a
factory receiving `ExtensionAPI`:

- **Register**: `registerTool`, `registerCommand`, `registerShortcut`, `registerFlag`,
  `registerProvider`, `registerMcpServer`, `registerVirtualModel`, and renderers for
  messages, entries and tools.
- **Act**: `sendMessage`, `sendUserMessage`, `appendEntry`, `setSessionName`, `exec`,
  `setActiveTools`, `setModel`, `setThinkingLevel`, an `events` bus.
- **UI** (`ExtensionUIContext`): `select`, `confirm`, `input`, `notify`, `editor`,
  `setStatus`, `setWidget`, `setFooter`, `setHeader`, `onTerminalInput`.
- **Events** via `on(name, handler)`, about 50 names: `input`, `before_agent_start`
  (add a message or replace the system prompt), `context` (replace messages), `turn_*`,
  `message_*`, `tool_call` (block, or mutate `event.input`), `tool_result` (replace
  content, details, `isError`), `tool_execution_*`, `user_bash`, `before_provider_request`,
  `model_select`, `session_start`, `session_shutdown`, `session_before_switch|fork|compact|
  tree` (can cancel), `session_compact`, `resources_discover`, `project_trust`.

**Skills** are `SKILL.md` folders under `<agent-dir>/skills`, `.pi/skills`,
`~/.agents/skills`, `.agents/skills`; only name and description enter the prompt, the body
loads on demand, `/skill:name` invokes one. **Prompt templates** (`prompts/`) become slash
commands. **Themes** are JSON. **Pi packages** bundle extensions, skills, prompts and
themes: `pi install npm:<pkg> | git:<url> | <local path>`, `pi list`, `pi remove`,
`pi update`, recorded in `settings.json`.

Built-in extensions in `src/extensions/`: `codemode` (script sandbox over tools), `mcp`
(MCP servers from `mcp.json` in the agent dir or `<project>/.pi/mcp.json`, tools named
`mcp__<server>__<tool>`, exposure mode codemode by default), `llama`, `tool-search`.

## 5. Supporting libraries

- **pi-tui.** Differential renderer: render the component tree to lines, composite
  overlays, diff against the previous frame, rewrite only the changed range inside
  synchronized-output markers; a full redraw on width or height change. `TuiMainScreen`
  keeps scrollback, `TuiAltScreen` owns a fixed viewport with mouse. `Component` is
  `render(width): string[]` plus optional `handleInput`; components include `Container`,
  `Text`, `Input`, `Editor`, `Markdown`, `SelectList`, `Loader`, `Image`. Keys: kitty
  keyboard protocol with a modifyOtherKeys fallback; `KeybindingsManager` makes bindings
  configurable. An optional native addon provides the clipboard only.
- **pi-mcp.** Own MCP client (protocol 2025-11-25, negotiating down), stdio and streamable
  HTTP transports, tools, resources, progress and cancellation, OAuth (discovery, PKCE,
  dynamic registration, refresh). Prompts, sampling, elicitation and batch JSON-RPC are not
  supported.
- **pi-codemode.** QuickJS (WASM) sandbox; the only capability is calling injected tools,
  so nested calls never enter model context. Runtimes: a worker thread per execution on
  Node or Bun, a remote Durable Object, or inline on the caller's thread. The sandbox
  persists nothing; `store`/`load` writes come back to the host.
- **pi-telemetry.** Contracts only (`startSpan`, metrics, propagation) with a no-op default
  and an in-memory reference adapter. Contexts are passed explicitly. Pi-durable uses it;
  the coding agent's own `core/telemetry.ts` is an unrelated install-telemetry opt-in
  (`PI_TELEMETRY`).

## 6. Quick answers

- *Where is persistence?* In `coding-agent` (`SessionManager`), not in `agent`.
- *Where do retries live?* In `AgentSession`, using helpers exported by `ai`.
- *How do I stop a tool batch?* Return `terminate: true` from every result in the batch.
- *Can two clients drive one session?* Not in this harness; RPC is one client over pipes.
- *Is a crash recoverable mid-turn?* The session file survives up to the last complete
  message, and `-r` resumes the conversation, but interrupted work is not re-run. For
  that, see `pi-durable`.
